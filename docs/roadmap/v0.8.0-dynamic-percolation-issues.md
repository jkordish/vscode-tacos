## Epic Hierarchy

### E1. EPIC: Percolation Policy Engine and Explainable Surfacing
1. Title
- EPIC: Percolation Policy Engine and Explainable Surfacing

2. Problem
- TaCoS currently has distributed ranking/suppression logic (`summary`, `nudge`, `presentation`) with no single decision layer.

3. Why now
- `v0.7.0` introduced mature surfaces; `v0.8.0` needs policy cohesion before more UI breadth.

4. Outcome / user value
- users see the right action with clear reasons and fewer low-value interruptions.

5. In scope
- candidate schema, ranking, suppression, explanation payload, per-context dismissal memory.

6. Out of scope
- cloud personalization, non-deterministic ML ranking.

7. Dependencies
- E4 signal normalization work.

8. Success metrics
- lower forced-open rate, improved primary CTA follow-through, stable notification dismiss rate.

9. Risks
- score thrash and over-suppression.

10. Definition of done
- policy emits deterministic decisions with explainability payload and tests.

11. Suggested milestone
- `v0.8.0-dynamic-percolation-core`

12. Suggested labels
- `epic`, `area:policy`, `v0.8.0`, `safety`, `performance`

13. Child issue list
- DP-101, DP-102, DP-103, DP-104, DP-105, DP-106

Decision rationale
- Build deterministic policy before introducing adaptive weighting.

Assumptions
- Existing summary/evidence generation remains the base candidate source in `v0.8.0`.

Tradeoffs
- Faster explainability and testability now, less personalization early.

Rejected alternatives
- Learned opaque ranker in `v0.8.0`.

Failure modes to avoid
- score oscillation that causes repeated emphasis changes.

### E2. EPIC: Adaptive Surface Architecture
1. Title
- EPIC: Adaptive Surface Architecture

2. Problem
- panel and status surfaces are stable but not yet policy-coordinated.

3. Why now
- without coordinated surface arbitration, dynamic percolation will feel bolted-on.

4. Outcome / user value
- stable layout, dynamic emphasis, fewer interruptions.

5. In scope
- top-card slot policy, section defaults, status bar elevation rules, notification broker, single-primary CTA rule.

6. Out of scope
- full panel redesign.

7. Dependencies
- E1 policy decisions and explainability payload.

8. Success metrics
- reduced prompt fatigue, improved first-action lag.

9. Risks
- layout churn or duplicated primary actions.

10. Definition of done
- one-primary CTA invariant and deterministic surface selection across status/panel/notification.

11. Suggested milestone
- `v0.8.0-dynamic-percolation-core`

12. Suggested labels
- `epic`, `area:companion-ui`, `v0.8.0`, `a11y`

13. Child issue list
- DP-201, DP-202, DP-203, DP-204, DP-205, DP-206

Decision rationale
- Preserve current panel structure and focus on policy-driven emphasis.

Assumptions
- Users benefit more from stable placement than frequent re-layout.

Tradeoffs
- Lower visual novelty, higher scan consistency.

Rejected alternatives
- dynamic card reordering based on every score recompute.

Failure modes to avoid
- duplicate primary CTAs and attention thrash.

7. Dependencies

8. Success metrics

9. Risks
- overfitting to noisy terminal/debug signals.

10. Definition of done
- typed signal bundle consumed by policy engine with deterministic tests.

11. Suggested milestone
- `v0.8.0-dynamic-percolation-core`

12. Suggested labels
- `epic`, `area:signals`, `v0.8.0`, `performance`

13. Child issue list
- DP-401, DP-402, DP-403, DP-404, DP-405, DP-406

Decision rationale
- Policy quality is bounded by signal quality; ingestion must lead.

Assumptions
- Existing hooks (task/debug/editor/focus/git) can provide enough deterministic features.

Tradeoffs
- upfront data-modeling effort to reduce downstream policy churn.

Rejected alternatives
- tuning ranking first and backfilling signal semantics later.

Failure modes to avoid
- noisy or duplicated signals dominating percolation scores.

3. Why now

4. Outcome / user value

5. In scope

6. Out of scope

9. Risks
- metric drift without stable definitions.

10. Definition of done
- metrics dictionary, tests, smoke runbook, and rollout checklist updated and passing.

11. Suggested milestone
- `v0.8.0-dynamic-percolation-core` then `v0.8.x-dynamic-percolation-tuning`

- `epic`, `area:metrics`, `area:testing`, `docs`

13. Child issue list
- DP-501, DP-502, DP-503, DP-504, DP-505, DP-506

- Launch decisions should be metrics-gated and reversible.

Assumptions
- local-only metrics are sufficient for release confidence in this phase.

Tradeoffs
- more instrumentation work now, fewer subjective regressions later.

Rejected alternatives
- shipping without percolation-specific metrics and relying on anecdotal feedback.

Failure modes to avoid
- metric schema drift and unverifiable \"calmer UX\" claims.
